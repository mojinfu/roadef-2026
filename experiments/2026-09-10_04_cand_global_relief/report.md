# 2026-09-10_04 候选集漏掉最优单点的概率：量化 + 全局 relief 兜底修复

## 0. 一句话结论

问了两个问题：「候选集漏掉最优解的概率能量化吗」和「质量怎么提升」。答案是：

1. **能量化，但要先把「最优」定义清楚**。以「全节点暴力枚举能给出的最好单waypoint列」为参照，
   `_03` 那版生成器在 **14/521 = 2.69% 的 live family** 上**一个可用单点都没给出**
   （不是「给了个差的」，是 `n_w1 = 0`、relief 0.000000）；受影响的是 **4/19 = 21% 的实例**。
   最惨的一族丢掉 relief **76.087** 的卸载机会（setA-10 demand 290 slot 0）。
2. **这个洞已经堵上并测过**：`-global-k 8` 后 capture = **19/19 实例全部 1.0000**，
   代价 **+0.2 ~ +1.1 ms/family**（20 实例候选总耗时 1352 → 2314 ms，+963 ms）。
3. **但它不等于「漏掉全局最优的概率」**。参照只枚举单waypoint，而 `cand` 输出 79% 是两waypoint；
   「全局最优」还牵涉多 demand 组合与 MIP 本身。所以下面给的是**一个定义明确、可复现的概率**，
   不是那个更大的东西——这一点在 §4 讲清楚。

## 1. 把问题变成可测的

「候选人选取方案有概率无法囊括最优解」这句话里的「最优解」有三层，能测的只有第一层：

| 层 | 定义 | 能否量化 |
|---|---|---|
| L1 | 该 family 上**单waypoint**能达到的最好列（即暴力枚举的 top-1） | ✅ 可精确判定 |
| L2 | 该 family 上**任意 waypoint 数**能达到的最好列 | ⚠️ 需要两waypoint 暴力枚举（未做） |
| L3 | 全局最优解里这个 demand 实际用的那一列 | ❌ 需要知道最优解本身 |

`_03` 的 `relief capture = cand 最优单点 / 暴力枚举最优单点` 就是 L1 的判定量。
它有两条性质使它可靠：**(a)** 两边都是「单waypoint 的 relief 最优值」，同类比同类；
**(b)** 对 MIP 来说重要的不是「哪个节点」而是「哪一列负载向量」，所以用 relief 值比较是对的
（两个不同节点给出同一列是无关紧要的）。

## 4. 必须说清楚的三个限定（否则这些数字会被过度解读）

**(a) 69.0% 里绝大部分是机械收益，不是策略变好了。**
`globalRelief` 取的是「按 relief 排序的 top-K」，而参照就是「按 relief 排序的 top-12」——
两者是**同一个函数**。所以 `-global-k 8` 必然拿下 top-12 里的 8 个，
`recall@12` 的**机械地板就是 8/12 = 66.7%**。实测 69.0%，也就是说策略本身只多贡献了 **2.3 个百分点**。
**capture = 1.0 同理，是构造性成立的**：它衡量的是「洞在不在」，堵上之后它就不再是质量指标了。
→ 结论：**修复后 `recall@12` 不再是可用的策略质量指标**，别再拿它横向比较下一版策略。

**(b) 剩余 31% 的 recall 缺口是 top-12 里的第 9~12 名，其 relief 很低。**
这些是低收益节点，漏掉它们对目标函数的影响没有任何证据支持——不构成「漏掉最优」的证据。

**(c) 真正的未知在 L2（两waypoint）。**
本实验的参照只枚举单waypoint。`cand` 输出里 **79% 是两waypoint**，这部分**完全没有参照**，
所以「候选集漏掉该 family 真正最优列的概率」**目前测不出来**。这是当前度量最大的盲区，
也是下一步该补的东西（见 §6）。

## 5. 成本与一个脆弱的边界

- 单实例 60 族：+16 ms（setA-10）到 +67 ms（setA-16）；20 实例合计 +963 ms。
- 逐族 +0.2 ~ +1.1 ms。O(n) 次真实路由/族，且与策略共享 `routeMemo`，策略已路由过的节点是 map 命中。

**脆弱点：`MaxW1 = 24` 的余量只剩 1。** 打开 global-k 8 后 w1/family 最高到
**23**（setA-14），其次是 22（setA-08）。而 `cand.go:353` 的截断是

```go
sortByRelief(w1)          // sort.SliceStable, 只按 relief，不按 tag
if len(w1) > opts.MaxW1 { w1 = w1[:opts.MaxW1] }
```

`SliceStable` 在**relief 相等**时保留先来者，而 global 节点是**追加在策略节点之后**的
（`cand.go:283`）。所以一旦边界上出现 relief 并列，被截掉的会是 global 节点——
capture 会**静默地**退回 < 1。现在还没触发（最高 23 < 24），但只差一个节点。
建议二选一：`GlobalK > 0` 时把 `MaxW1` 抬到 `MaxW1+GlobalK`，或在截断前把 `TagGlobal` 的节点前置。

## 6. 建议（按性价比排序）

1. **把 `-cand-global-k 8` 设为默认**（现在是 0，opt-in）。它关闭的是一个**已证明存在**的洞
   （14 族零单点，最惨一族丢掉 relief 76.09），代价可忽略。但在改默认值之前，
   应该先跑一次**针对性整解 A/B**：只跑 setA-04/10/13/16 四个实例（洞真实存在的那些），
   每个都跑 ≥3 次配对——因为在别处它只是多给几列，在这四个上它可能直接把首bit打下来。
   注意整解 A/B 的 Gurobi 噪声 ~7.7%（`_03` §1），必须配对 + 重复。
2. **补两waypoint 暴力参照**，这是当前度量的最大盲区（§4c）。可行做法：在 n≤50 的实例
   （setA-01/02/03/04）上对 C(n-2,2) 配对做一次真实路由枚举，得到 L2 的 capture。
   不做这一步，下一版策略的「质量提升」就没有可比的标尺。
3. **修 §5 的截断脆弱点**（低风险，防静默退化）。
4. **下一个杠杆不在 hop ball 半径，而在配对上**。setA-15/17/20 的 w1/family 塌到 1~2 曾是
   头号问题，但 global-k 已经从单点侧补掉了它（setA-15 recall 3.1% → 65.6%）。
   现在 ball 只影响**成对材料**（`hot_center` 的 offload 测试只把 ball 内节点变成 pair 素材），
   所以资源应该投在「两waypoint 的生成与选择」上，而不是继续放宽 `MaxExtraHop`。
5. **考虑让 global 节点也当配对材料**。目前刻意不（注释说是为了控制 MIP 规模），
   但「最优单点 + 一条 detour 节点」正是能同时卸两条弧的组合，值得一次小规模 A/B。
6. **不要在跳数缓存上继续投性能预算**（`_03` §3：BFS 从来不是瓶颈）。

## 7. 复现

```bash
cd solution
go build -o ../_pyref/candbench.exe ./cmd/candbench
# 缺口明细（修复前）
python -c "见 report 内联脚本"   # 输入 experiments/2026-09-10_03_cand_microbench/data/tsv/
# 修复后 sweep
for i in $(seq -w 1 20); do
  ../_pyref/candbench.exe -prefix ../setA/setA-$i -hot-k 6 -max-families 60 \
      -recall-k 12 -global-k 8 > runs_candbench_gk8/setA-$i.txt
done
# 单族对照（有/无兜底）
../_pyref/candbench.exe -prefix ../setA/setA-10 -hot-k 6 -max-families 60 -recall-k 12 -global-k 0
../_pyref/candbench.exe -prefix ../setA/setA-10 -hot-k 6 -max-families 60 -recall-k 12 -global-k 8
```

`cmd/candbench` 本次新增 `-global-k`（此前该开关只存在于 `solve`，兜底策略从未被测过）。
