# exp01 — v0.1 求解器在 setA 上的基准结果

- 日期：2026-09-05（**2026-09-06 用 checker-fix 代码重跑并更正倒序节点实例**）
- 代码版本：见 `meta.json`（HEAD commit `e93ef7e`，branch `main`）
- 求解器：v0.1 —— 单 waypoint（+空路径）增量局部搜索，多起点，字典序 trunc6 目标
- 测试集：setA 全部 20 实例（官方数据）
- 运行参数：每实例 20 s 求解预算 × 2 restarts（`scripts/bench_setA.py --solver v1 --time 20 --restarts 2`）
- 原始输出：根目录 `runs_benchA.log`（本目录 `data/` 有一份拷贝）、解文件 `runs/setA-XX-srpaths.json`

## 1. 方法与参照

- 基线 = 全部空 waypoint（纯 IGP/ECMP 最短路径路由，slot 0 无干预；slot 1 去掉干预弧）。
- ECMP 实现与官方 checker 逐值一致（精确等于放松条件，见 exp02 交叉验证）。
- 目标函数 = 按负载降序的饱和向量，逐项截断到 6 位小数后的字典序最小化（与官方 checker 一致）。
- 参照 = `sprint_results/loads_vector.csv`：每个实例第一名（提交中严格最优）的负载向量。
- 预算语义 = 各需求 slot0→slot1 路径的 checker `dist` 之和（空路径=含 `(s,t)` 掩码位），
  `tasr/algos/search.py::path_distance` 已核对与官方一致（见 exp02）。

## 3. 更正说明（相对 2026-09-05 初版）

初版用倒序节点 id 的实例（setA-05/08/12/14/17）按文件 id 当位置路由，曾得到错误结果，
并把 setA-12 报成"好于 sprint"。2026-09-06 在修复 id/位置映射、并把 ECMP 改为与 checker
逐值一致的精确版本后重跑，得到：

- 倒序节点实例数值全部更正；setA-05/17 的 max 负载与参照逐位相同（截6），
  setA-08/14 接近参照，setA-12 现在与基线一致收敛到参照的 top（0.879872），
  **不再出现"好于 sprint"的异常**（exp02 的 checker 交叉验证证实本模型与官方一致）。
- 部分大数据量实例（setA-06/13/16/19）在同一批重跑中结果也有小幅波动，
  根因是 v0.1 的局部搜索随机性；下表以本次 `runs_benchA.log` 为准。

## 4. 结论

1. **max 负载（字典序第 1 分量）**：13/20 实例与 sprint 第一名截6 相同（本表只比了第 1
   分量，不是整条向量）：
   setA-01/02/03/05/07/08/09/11/12/15/17/18/20。其中多数是从 ≥1.0 的拥塞基线压下来的真实成果；
   setA-18 的 0.999998 本质不可避（参照同样 ≈1.0）。
   ⚠️ 整条负载向量与 sprint 参照**打平 0/20**（差距落在 max 之后各层的量化表见
   exp03 §3 与 exp03 `data/sprint_gap_by_layer.tsv`）。
2. **整条负载向量**：除前列同 top 的实例外，尾部仍差于参照——只追平第 1 个分量，
   第 2 个分量起的均衡没有做。这是 v0.1 邻域（一次只改一个需求的一个 waypoint）的能力上限。
3. **远落后实例**（setA-04/06/10/13/14/16/19）：参照的 max 负载低至 0.04-0.52，
   需要把流量沿多条走廊摊开。其中 setA-10/13/16/19 预算 ≤13，几乎只允许"双槽同路径
   （twin）"，v0.1 只做单 waypoint twin，无法进一步摊薄 → 需要 v0.2（多段 twin + 协同移动，
   见 exp03）。
4. **v0.1 的现实意义**：ECMP/评估/预算三层已与官方 checker 逐值一致（exp02），
   v0.1 的所有输出都可直接提交验证；质量瓶颈在邻域表达能力而非评估正确性。
