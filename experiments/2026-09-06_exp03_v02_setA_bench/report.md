# exp03 — v0.2 求解器（多段 twin + 协同移动）setA 基准

- 日期：2026-09-06
- 代码版本：见 `meta.json`（HEAD commit `e93ef7e`，branch `main`；`tasr/algos/search_v2.py`
  与 `tests/test_search_v2.py` 为该实验新增、运行后一并提交）
- 求解器：v0.2（`tasr/algos/search_v2.py`）
  - 邻域：单点编辑（插入/替换/删除 waypoint）上的三种移动族
    - `twin`：需求双槽设为同一条多 waypoint 路径（预算 0，紧预算主力）
    - `single`：只改一槽（多 waypoint 版 v0.1）
    - `shift`：先 twin 掉一个发散需求释放预算，再花到另一个需求的单槽改路
  - 驱动：最优改进下降；候选需求按**瓶颈优先**（最热 (arc,slot) 上的大流量需求优先）
  - waypoint 池：每需求每扫描随机抽 60 个纯随机节点
- 测试集：setA×20；参数 60 s/实例 × 1 restart（`scripts/bench_setA.py --solver v2 --time 60 --restarts 1`）
- 原始输出：`data/runs_benchA_v2.log`、解 `runs_v2/*.json`
- checker 交叉验证：`data/checker_xval_v2.log`（对 `runs_v2/*`，40/40 PASS，见 §3）

## 1. 动机

exp01 的瓶颈实例（setA-06/10/13/16/19 等，预算 1/13）要求把流量摊到多条走廊；
预算按需求求和、同路径双槽距离为 0 → 结构上只允许"twin"。v0.1 只会单 waypoint twin，
单点无法表达多走廊摊薄，所以 max 负载卡在 0.36-0.91。v0.2 的目标：多 waypoint twin +
协同移动，把紧预算实例压到参照附近。

## 4. 结论

1. **紧预算假设被证实**：setA-06/10/13/16/19 全部以 `dist=0` 的纯多段 twin 得到巨大改善，
   max 负载分别降到参照的 1.1×/1.3×/3.3×/8.9×/12×（原为 3.7×/8×/17×/19×/19×）。
   剩余差距集中在"需要极多走廊摊薄"的大需求实例（setA-16/19：4800/6000 需求、参照
   max 仅 ~0.044/0.047），单点编辑 + 60 节点随机池的表达还不足以铺开到参照的精细度。
2. **单次 best-improvement 下降的尾部不稳**：整向量 10/10 分边，说明 v0.2 以 60s×1
   restart 跑出的解，在 max 已持平的实例上会收敛到尾部更差的局部最优。→ 生产提交应
   **每实例取 v1/v2 更优者**（即本表 winner），或 v0.2 加多 restart + 尾部扰动。
3. **多段 twin 是紧预算实例的正确结构**，但协同 `shift` 在当前瓶颈优先候选下几乎没有
   被触发（多数发散需求本身就在改善路径上），v0.3 应重新考虑 shift 的触发条件。
4. **评估链已可信**（exp02 + 本节）：所有 v0.2 输出可直接提交；剩余工作纯属搜索质量。
