## 1. 目标与动机

当前 v0.2/v0.3 的候选池（随机 60 或 corridor 增广）在超大实例上的问题是**规模无关的盲目**
——绝大多数求值落在"与该需求当前热点走廊无关"的节点上。本方案改为**因果驱动**：
先锁定当前负载最高的 A→B 流，再在它周围**局部挖一个候选管带**，压缩成最少 waypoint，
最后在预算内挑"最能给最热路径分流"的那条。候选规模只与"步长"相关，不随网络总节点数膨胀。

## 2. 算法流程（按用户原述整理）

### 2.1 提取当前占用核心带宽最高的 A→B 最热路径

锁定当前最热点（最拥塞弧/路径），取其承载的 A→B 流作为本次改造对象。

### 2.2 设定步长，双向受限搜索取交集 = 候选池

1. 设定探索步长 k；
2. 从 **A 出发向下（正向）深度/广度搜索**步长 k，得到节点集合 `S_A = {C : d(A, C) ≤ k}`；
3. 从 **B 出发向上（反向）溯源**同样步长 k，得到 `S_B = {C : d(C, B) ≤ k}`；
4. 候选中间节点池 = `S_A ∩ S_B`（位于 A、B 之间"管子"内的节点）。

这样候选规模是 `O(步长内节点数)`，与全图 N 解耦——这是超大网络下可负担的关键。

### 2.3 对候选池中的新 A→B 路径做最简 waypoint 压缩

对候选池里的每个 C（进而得到 A→…→C→…→B 的候选路径），做**最简 waypoint 压缩**：

- 依次判断路径上的每个中间节点 Y；
- 若 `dist(X, Y) + dist(Y, Z) == dist(X, Z)`（X、Z 为 Y 前后相邻的保留锚点），说明 Y 落在
  X→Z 的最短走廊上、可省略（不是真实转折点）；
- 仅保留**不可省略的转折点**作为 waypoint。

由此同一候选路径可得到 1…`max_segments−1` 个不同长度的最简 waypoint 方案。

### 2.4 预算约束下，选"分流最热路径负载最大"的方案

结合预算额度（waypoint 数量上限 `max_segments`、以及跨时隙改路预算 budget），
从上面形成的最简方案中，优先选择**能最大程度分流最热路径负载**且满足预算约束的那个。

## 3. 与现有代码/概念的关系

| 本方案概念 | 现有对应物 |
|---|---|
| A 向下搜索、B 向上溯源 | `candidates.py::DistanceIndex.fwd/rev`（按 (节点,时隙) 缓存最短距离） |
| 节点处于 A、B 之间的走廊 | `candidates.py::leg_corridor` 的 slack=0 DAG 内部节点 |
| 最简压缩的判别 `dist(X,Y)+dist(Y,Z)==dist(X,Z)` | ECMP `compute_atom` 里紧弧/转发图判定同款精确 `==` 语义 |
| 最热路径选择 | `search_v2.py` 的瓶颈优先 demand 选择（top 弧 → 贡献排序） |
| 输出 waypoint 方案 | 即 `srpaths.json` 中 `w` 列表 |

上一版实测结论（见 `experiments/` 与 search_v3 迭代记录）：**corridor 类候选在"尾部均衡"
上有正收益，但在"压 max 需要远绕行"的实例上不如纯随机**。本方案本质上把 corridor 再收紧为
"步长管带 ∩ 最简压缩"，因此**必须**在 §5 里厘清它对远绕行的表达力，避免重蹈 v3 覆辙。

## 4. 补充分析（实现前必须先想清的技术点）

1. **ECMP 下"路径"不是唯一节点序列。** 任意 A→C 段实际流量摊在整个转发图 FG(A,C) 上；
   "从 A 到 C 的路径"与"压缩判别用的节点序列"都需要定义（选一条显式最短路径？还是在
   FG 上定义）。这决定压缩结果与真实 ECMP 负载的偏差。
2. **最简 waypoint 只切开走廊，不锁定走廊内路由。** 保留相邻 waypoint X→Z 之间仍是 ECMP
   多路径。若 X→Z 之间存在与最热弧平行的等代价弧，压缩并不能保证把热弧移出走廊——
   压缩的语义要按"分流目标"重新校准，而非纯粹的最少段数。
3. **步长取跳数还是 metric 距离**直接决定管带形状与候选质量；metric 取值在网络间差异大，
   跳数更scale-free 但对 ECMP（按 metric 分裂）失真。
4. **"最大程度分流"的度量**：局部代理（热弧负载下降量）便宜但可能与字典序全局目标相悖
   （可能在别处制造新的更大热弧）；全局精确评估每个候选又贵。需要定"代理筛选 + top-k
   精确评估"的分层。
5. **单条最热流的改造 vs 一条热弧上多流共享**：超大实例单弧往往由成千需求各贡献一点，
   "最大贡献单需求"未必是最好杠杆；是否需要对热弧做多需求协同（一次改造一组）？
6. **与预算的接口**：本方案每次对单个 (demand, slot) 生成几条 waypoint 方案，最终挑选
   还要看 twin（双槽同路、dist=0）vs single（仅改 t=1、消耗 budget）的组合语义。

## 5. 开放问题（实现前需与提出者澄清）

- **OQ1 步长语义**：k 按"跳数"还是"metric 距离"？向下/向上是否只沿能成为 A→B 路径的
  最短路径 DAG 走，还是沿全图任意出弧？
- **OQ2 最热 A→B 路径的对象口径**：取全局字典序最高负载弧上贡献最大的单条 (demand, slot)
  流（A=d.source, B=d.target）？还是某个显式分支路径？ECMP 分流下"单条最热路径"需定义。
- **OQ3 候选池 → 路径 → 压缩的对象**：交集里的每个 C 是直接当单 waypoint 用，还是先构造
  一条 A→C→B 的显式节点序列路径再压缩？若 A→C 是 ECMP 转发图（非唯一路径），压缩基于哪条
  路径？
- **OQ4 压缩的取舍**：接受"waypoint 只负责把热弧移出走廊"的近似，还是要精确复现某条显式
  路径？若热弧位于 X→Z 某条等代价分支上，允许保留"多余"waypoint 强行切掉该分支吗？
- **OQ5 方案枚举范围**：一组转折点要输出"全部子序列长度 1..k"的变体，还是只输出
  "全转折"和"压缩到最短"两种？
- **OQ6 预算口径**："waypoint 数量符合预算"指的是 (a) ≤ max_segments−1，(b) 跨时隙
  dist 预算，(c) 两者？改造 slot1 时 slot0 固定为当前路径、用 twin 则双槽同路？
- **OQ7 分流评估层级**：候选择优用全局字典序精确求值，还是先用局部代理筛 top-k？
- **OQ8 迭代粒度**：每轮只处理"最热一条流"并重算，还是一次选多条热点流并行生成？
- **OQ9 退化兜底**：A、B 距离大于 2k 导致交集为空/过小时，放大 k 还是回退 metric 走廊
  或随机池？
